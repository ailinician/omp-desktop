# Steer / follow-up queue

omp owns the queue. A message sent while the agent works — the send key mid-turn (`OMP_BRIDGE.steer`; Enter or Ctrl/⌘+Enter per Settings → Composer `submitKey`), `app.message.followUp` (`followUp`), approve-plan's `APPROVAL_PROMPT` — goes out as an id-correlated `steer` / `follow_up` (or `prompt` with `streamingBehavior`, see the commands bullet under *Things easy to break*) and gets **no transcript bubble**: omp holds a follow-up until the agent would otherwise stop and a steer until the current tool batch ends, and either can be removed meanwhile. It joins the transcript as its `message_start` echo, tagged `echo` so `scroll-pin.js`'s `shouldRepin` leaves a reader where they are (a plain `send` still shows its prompt at once, and its echo dedupes against that untagged tail bubble). Until then the composer's queue strip (`design/queue-strip.jsx`) shows it; the pure helpers are `src/app/message-queue.js` (`window.OMP_QUEUE`, regression `test-message-queue.mjs`).

- `state.queue` is exactly omp's snapshot — every `queue_update` frame and `get_state.queuedMessages`, last one in the stream wins — and is never edited locally. Its texts are omp's queue-chip texts (first text part, templates expanded, `/skill:` calls as typed, `"[Image]"` for an image-only message). Steering also lists messages the model already took, until the transcript records them.
- `state.queueSending` holds a "sending" row per send omp has not acknowledged yet (the acknowledgement comes at admission, after any image preparation — seconds with a vision description). The row hides once omp lists its text one more time than it was queued or in flight when sent, and is dropped by the response, wherever its tab's state lives by then (`_dropSending`). A refusal files a note carrying the text; a timeout only drops the row. Both fields are per tab in the four usual places, and a process exit clears both (the exit listener, or the `session_status` death of a background tab).
- A `/skill:` call is not a `user` message in omp: it reaches the model as a `skill-prompt` custom message (content = the whole skill file). Its echo is rendered from `details.prompt`; `adaptAgentMessages` never builds an entry from a custom message, so the get_messages merge has no copy for that bubble and leaves it in place.
- ✕ / ✎ → `remove_queued_message`, ↑ (follow-ups) → `promote_queued_message`. `removed`/`promoted: false` means the message was no longer pending (delivered, or already taken by the model) — the strip says "already delivered". Rows only ever disappear through omp's next snapshot. omp acts on the *first* matching text, so the strip allows one request at a time; a repeated request would hit the next duplicate. ✎ puts the text back (not the images — the queue does not return them) only after `removed: true`, into the tab it was queued from. Never fall back to aborting, resending or `steer` (omp's `docs/rpc.md`).
- After a user abort omp keeps both queues: steers resume on their own, follow-ups wait — ↑ on one starts a turn right away.
- ⚡ "send now" (#47, only while the agent runs, `OMP_BRIDGE.sendQueuedNow`): a follow-up is promoted to a steer first (`promoted: false` → "already delivered", nothing aborted), then the running step gets the same id-less `abort` as Esc, and omp resumes at once with its steering queue (agent-session `#drainStrandedQueuedMessages`) — every queued steer, this one included, with its images, since nothing leaves omp's queue. The abort is the whole of Esc: a running command is killed, a goal pauses. Skipped when the run ended meanwhile (the promote alone starts the turn), when an abort is still in flight (`userAbortInFlight`: a second ⚡ or a double click would otherwise stop the resumed reply to the steers just taken), or after any tab switch during the promote (`_switchGen`, not the active id: a reply held back by A→B→A is replayed on the way back, when A's run has moved on) — the message then goes at the next step. Measured on omp 18.10.1, for a steer and a promoted follow-up alike: the abort's `turn_end`, `agent_end` and response, an emptied `queue_update`, then the resumed `agent_start`/`turn_start` with the message — so `userAbortInFlight` and then `state.isStreaming` (false from `turn_end`) leave no gap for a second abort. Not `abort_and_prompt`: that would need the message out of the queue first, and only omp ≥ 18.6.3 returns its images from `remove_queued_message`. A steer the model already took is still listed until the transcript records it; ⚡ on it in that window stops the reply to it.
